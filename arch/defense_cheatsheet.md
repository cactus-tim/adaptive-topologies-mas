Коротко, по каждому вопросу — готовый устный ответ в 2–4 предложения.

## 2. E1 — лучшая топология для каждой задачи

| Задача | Топ-1 топология | quality_score | Почему побеждает |
|---|---|---|---|
| **HumanEval** (programming) | **Chain** | 0.82 | линейный pipeline Planner→Executor→Critic с retry-loop по unit-тестам — идеальный фит для code |
| **GSM8K** (math) | **Debate** | 0.85 | два Debater'а генерируют альтернативные reasoning-пути, Judge выбирает правильный — решает проблему ошибок в CoT |
| **CommonGen** (creative) | **Debate** | 0.66 | разнообразие вариантов критично для open-ended задач; Judge ранжирует по coverage концептов |
| **InfiAgent-DABench** (numeric analysis) | **Chain** | 0.62 | последовательный анализ данных + code-sandbox у Executor; Critic проверяет числовой ответ |

**Паттерн:** Chain для задач с объективной проверкой (тесты, числа), Debate для задач с открытым пространством решений.

## 3. Роли человека — Peer и Monitor (остальные для контекста)

| Роль | Суть | Когда активна |
|---|---|---|
| **Coordinator** | Ведущий, раздаёт задания, синтезирует ответы агентов | Mesh, Hierarchical — где нет встроенной координации |
| **Reviewer** | Ревьювит каждый draft, отправляет на переделку | Chain, Star — как усиленный Critic |
| **Judge** | Финальный арбитр, выбирает из альтернатив | Debate — natural fit |
| **Peer** | **Равный участник** — не сверху, а вносит альтернативные мнения наравне с агентами | Mesh — вписывается в round-robin; **исключён в Chain/Hierarchical**, потому что ломает иерархию |
| **Monitor** | **Пассивный наблюдатель** — молчит, вмешивается только в критические моменты (budget overruns, зависания, повторы) | везде; основной вклад — не quality, а снижение `failure_rate` |

**Ключевое различие Peer vs Monitor:** Peer — активный участник наравне с агентами (генерирует контент); Monitor — внешний safeguard, генерирует только при проблеме.

## 4. Что такое Pareto-фронт

**Граница оптимальных решений** в многокритериальной оптимизации. Конфигурация **на фронте** означает: нельзя улучшить одну метрику (например quality), не ухудшив другую (cost или time).

Конфиг **за фронтом** (dominated) — тот, для которого найдётся решение строго лучше по всем осям одновременно.

**В нашем случае:** по 3 осям (quality × cost × time) строим фронт 5 топологий. Chain (cheap, средне по quality), Debate (дорого, max quality на reasoning) — оба на фронте. Mesh и Hierarchical почти везде dominated — за счёт overhead они не лучше Chain/Debate ни по одной оси.

## 5. Open-ended генерация с ограничениями (CommonGen)

**«Open-ended»** — правильных ответов бесконечно много, нет единого эталона.
**«С ограничениями»** — ответ должен использовать **все заданные концепты**.

**Пример CommonGen:** вход `{"dog", "frisbee", "catch", "throw"}` → любой ответ из семейства:
- "A dog catches a frisbee that is thrown by its owner."
- "The boy throws a frisbee and his dog catches it."
- ...

Задача бенча — проверить, может ли модель **связно скомбинировать** набор понятий в грамматически верное предложение.

## 6. ROUGE-L + concept coverage

Две метрики, усреднённые в одну оценку для CommonGen:

- **ROUGE-L (Longest Common Subsequence)** — метрика лексической схожести с reference-ответами. Смотрит длину самой длинной совпадающей последовательности слов между ответом модели и эталоном. Диапазон [0, 1], выше — ближе к эталону.
- **Concept coverage** — доля заданных концептов, реально использованных в ответе. Если из `{dog, frisbee, catch}` модель использовала 2 из 3 → coverage = 0.67. Строго бинарно по каждому концепту.

**Почему обе:** ROUGE-L ловит стилистическую близость, coverage — семантическую полноту. По отдельности обе обходятся: ROUGE высок, если скопировать reference; coverage высок, если перечислить концепты без грамматики.

---

## 7. Exact match на числе (GSM8K, InfiAgent)

**Бинарная метрика:** ответ засчитан (1), если финальное число в выводе **точно совпадает** с ground truth; иначе 0.

**Парсер:** извлекает последнее число из ответа или число внутри `\boxed{...}` (стандарт математических бенчей). Сравнивает с эталоном посимвольно (с нормализацией: "1000", "1,000", "1.0×10³" — один класс).

**Почему строгая метрика:** математическая задача имеет один правильный ответ. «Близко» не считается — `42` ≠ `43`. Исключает субъективность LLM-judge.

## 8. `oracle_gap_loo` — что такое

**oracle_loo** (leave-one-out oracle) — **честный верхний потолок** адаптации на уровне класса задач.

Как строится: для каждой задачи `t`
1. Берём результаты E1 — `(task_id, topology) → quality`
2. **Исключаем `t`** из агрегации
3. Находим `best_topology_for_type(task_type(t))` — лучшая топология по задачам **того же типа, кроме `t`**
4. Oracle для `t` = применить эту топологию

**oracle_gap_loo** = `quality_oracle_loo` − `quality_actual_router`.

**Смысл:** сколько quality router потерял по сравнению с идеальным выбором *по классу задач*. Честный bound — он не «подсматривает» ответ на конкретную задачу, только на её класс.

**Если gap малый** → router близок к потолку, адаптация почти максимальна.
**Если gap большой** → есть куда расти, правила/промпт router'а можно улучшить.

## 9. Rule-based router — как работает

**Детерминированная таблица** `(phase, signals) → topology`. Никаких LLM, работает за микросекунды, 100% воспроизводимо.

**Пример правил:**
```
if phase == planning:
    return Star                       # координатор раздаёт план
if phase == execution and signals.stuck:
    return Mesh                       # все агенты накидывают идеи
if phase == execution and signals.rejected_count >= 3:
    return Debate                     # спор решит тупик
if phase == verification:
    return Chain                      # линейная валидация
return current_topology               # иначе не переключаемся
```

**Плюсы:** быстро, детерминированно, дёшево (0 LLM calls), прозрачно для защиты.
**Минусы:** правила вручную прописаны по интуиции, не учатся на данных.

**В диссертации rule-based работает как safe default + baseline для сравнения с llm-router.**

## 10. `guard_override_rate` и `hurt_rate`

### `guard_override_rate`

Доля router-решений, которые были **заблокированы SwitchGuards** (защитными правилами против thrashing):
- `min_dwell` — минимум N итераций в одной топологии перед сменой
- `cooldown` — интервал между сменами
- `max_per_run` — лимит смен за прогон
- `max_per_phase` — лимит смен внутри одной фазы

**Интерпретация:** высокий rate (>30%) = router хочет переключаться слишком часто, guards его ограничивают; низкий (<5%) = router и так спокойный.

У нас: rule-based 20%, llm-router 25% — guards реально работают.

### `hurt_rate`

**Safety-индикатор.** Доля задач, где Adaptive дал `quality` **хуже**, чем best-static на той же задаче.

**Интерпретация:**
- `hurt_rate < 30%` — безопасно, adaptive регрессирует редко
- `hurt_rate 30–50%` — marginal, под вопросом
- `hurt_rate > 50%` — adaptive хуже чем ничего, нельзя включать по умолчанию

У нас: rule-based 22%, llm-router 19% — в безопасной зоне. Это ключевой аргумент, что «adaptive не вредит на большинстве задач».
