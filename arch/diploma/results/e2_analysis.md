## 1. Постановка (RQ3)

**RQ3.** *Как влияет вовлечение человека (HITL) с разной ролью на качество, стоимость и время мульти-агентного пайплайна разной топологии?*

**Гипотеза.** HITL-узел улучшает качество для топологий, где есть «свободный слот» для внешнего контроля (Reviewer / Judge / Monitor в Star / Hierarchical / Debate), и нейтрален либо вреден там, где он ломает поток управления (Chain). При этом каждая роль имеет своё предпочтительное соответствие типу задачи: Judge — для верифицируемых (HumanEval / GSM8K), Peer — для творческих и слабо-структурированных (CommonGen / DABench), Monitor — для длинных reasoning-цепочек.

**Почему симулятор, а не реальный человек.** На уровне E1–E4 человек заменён LLM-вызовом (`gateway: llm_simulated`, модель `openai:gpt-4.1-mini`, фикс persona-seed) по трём причинам, прямо зафиксированным в плане:

1. **Воспроизводимость.** 2 295 runs × 1–2 HITL-вызова на run = ~3 000 «человеко-актов»; повторить это с реальными участниками означало бы недели работы и контаминацию опытом.
2. **Стоимость.** Цена HITL-gateway-вызова через `openai:gpt-4.1-mini` ≈ $0.001; для всего E2 ($42.37) HITL-надбавка укладывается в единицы долларов вместо сотен долларов компенсации участникам.
3. **Cross-family независимость.** Worker-агенты крутятся на `cerebras:gpt-oss-120b`, judge — `openai:gpt-4.1-mini`, HITL-симулятор — `openai:gpt-4.1-mini`. Веса HITL независимы от worker-весов (разные родословные), что снижает риск артефакта «модель оценивает сама себя» — критичный аргумент для защиты, что прирост качества не сводится к самоодобрению Cerebras-pool'а.

Валидность LLM-симулятора как прокси реального человека вынесена в **E5** (real human study, 8–12 участников, NASA-TLX) — там же будет численная корреляция симулятор-vs-человек. В E2 эта проверка не выполняется по дизайну.

## 2. Дизайн эксперимента

**Сетка (план).** 5 топологий × 5 ролей × 4 task_types × 15 stratified задач × 3 seed = 4 500 ячеек брутто.

**Фактически запущено:** 2 295 ячеек (−49%). Сокращение обеспечено двумя фильтрами, реализованными в `scripts/run_e2.py`:

### 2.1 Per-(task, topology) фильтр из E1 top-3

Вместо глобального top-3 (где победитель «в среднем по больнице» рискует затереть task-specific сильные пары) используется **per-task top-3**, извлечённый из `analysis/e1_top3.json` (артефакт от E1, exp_id `f153400f-…`):

| Task | Top-3 топологии (по E1) |
|---|---|
| `humaneval` | chain, star, hierarchical |
| `gsm8k` | star, hierarchical, debate |
| `commongen` | debate, chain, hierarchical |
| `dabench` | debate, chain, mesh |

Объединение по задачам охватывает **все 5 топологий** (mesh попал только через dabench; star — только в gsm8k / humaneval). Это объясняет неравномерность `n` по топологиям в финальной выборке (см. §3): star имеет n = 450 (2 task'а × 5 ролей × 45), mesh — лишь n = 225 (1 task × 5 ролей × 45).

### 2.2 Исключение «структурно бессмысленных» (topology × role)

Жёстко выкинуты три пары:

- `debate × coordinator` — координатор семантически совпадает с judge в дебатах;
- `chain × peer` — в линейном пайплайне нет «параллельной» позиции для peer'а;
- `hierarchical × peer` — peer ломает иерархию команд.

В результате peer представлен только в `star`, `debate`, `mesh` (n = 270), а coordinator — в `chain`, `hierarchical`, `mesh`, `star` (n = 405). Это критично для интерпретации §4: «победа peer» опирается на меньшую выборку, чем «победа reviewer».

### 2.3 Прочие параметры

- **Worker-модель:** `cerebras:gpt-oss-120b` для всех ролей (planner / researcher / executor / critic / summarizer / router) — изолирована переменная модели.
- **Judge:** `openai:gpt-4.1-mini`, self-consistency × 3, temperature 0.0.
- **HITL-gateway:** `openai:gpt-4.1-mini`, `role_router: fixed` (фиксированная роль на ячейку — это ключевое отличие от E4, где роль будет адаптивной).
- **Iter-caps:** `chain.max_iterations = 6`, `star.exec_max_iter = 3 / verify_max_iter = 2`, `debate.max_rounds = 2`, `hierarchical.max_rounds = 2` — те же smart-cuts, что в E1.
- **Бюджет:** $0.05 / call, $0.40 / run, $80 / experiment (фактическое потребление $42.37 = 53% headroom'а).

**Главные наблюдения.**

1. **Peer × mesh = 0.60** — единственная клетка mesh, где качество выходит из ямы ≈ 0.34. Прирост +0.26 п.п. над coordinator. Гипотеза: peer как «равноправный voter» естественно встраивается в mesh-консенсус (где `consensus_threshold = 3`); другие роли пытаются «руководить» mesh-сетью и тем самым ломают round-robin voting.
2. **Peer × debate = 0.72** — лучший результат для debate; peer вступает дополнительным «голосом» в дебатах и улучшает покрытие.
3. **Monitor / Reviewer × star = 0.944** — формальный максимум по матрице; star + строгий внешний наблюдатель — устойчивая комбинация (см. §8 про сравнение с E1).
4. **Coordinator явно проседает в mesh (0.24)** — координатор пытается централизовать сеть, для которой архитектура заточена под децентрализованный voting; conflict producing low quality.
5. **Hierarchical стабильно высокий (0.81–0.84) для любой роли** — иерархия терпима к выбору HITL-роли; разброс по ролям ≤ 3 п.п. Это важный «безопасный default» для следующих этапов.

**Проверка утверждения коммита «peer wins overall (q=0.758)».** Подтверждается (см. §3.3). **«Peer dominates dabench (0.563 vs 0.21–0.39)».** Подтверждается с поправкой: peer-победа на dabench опирается на пару cells (`peer × debate = 0.526`, `peer × mesh = 0.600`) и связана с архитектурным fit'ом, а не с универсальной силой peer'а на «данных в табличках».

## 7. Ответ на RQ3

**Улучшает ли HITL качество?** В среднем — **да, но скромно**: ≈ +3.3 п.п. абсолютного прироста `mean_q` на сравнимых (task, topology) парах (+4.8% relative). Эффект **не равномерен** по сетке.

**Где HITL помогает.**
1. На **слабо-сходящихся комбинациях** (chain × dabench, hierarchical × commongen): HITL ломает «застой» цепи и подбрасывает альтернативу — лифт 7–11 п.п.
2. На **mesh с peer-ролью**: единственный способ заставить mesh работать на dabench (0.60 vs 0.32 у других ролей).
3. На **debate**: HITL как дополнительный «голос» стабильно даёт +4 п.п. независимо от задачи.

**Где HITL нейтрален или вреден.**
1. На **star + verifiable tasks** (gsm8k, humaneval): топология уже близка к потолку (≥ 0.91), HITL добавляет вызов на каждый цикл без эффекта; на gsm8k даже −0.06.
2. На **hierarchical + gsm8k**: −0.02 — то же.
3. На **coordinator × mesh** (0.24): дополнительное «централизованное руководство» вредит децентрализованной сети.

**Что это говорит о role-design.** Единая роль на весь эксперимент **не оптимальна**: разрыв «winning role per task» составляет 16 п.п. (coordinator-humaneval 0.95 vs peer-commongen 0.64 даже у победителей — масштабы разные, но и в пределах одного типа: peer-dabench 0.56 vs coordinator-dabench 0.21 — разница ×2.6). Это сильный аргумент для:

- **E3** — фиксировать **per-task winning role** при адаптации топологий (т.е. использовать таблицу §5 как «role-by-task default»);
- **E4** — испытать **adaptive role-router**, который меняет роль по фазе (planning → coordinator, execution → monitor, verification → reviewer). E2 не отвечает на вопрос «нужен ли adaptive-role», но даёт сильный prior, что **role matters** и единый фиксированный role-default — упрощение.

## 8. Аномалии и ограничения

### 8.1 Mesh всё ещё проседает

`mean_q(mesh) = 0.3704` — самая низкая среди 5 топологий, и HITL её спасает лишь частично (на dabench, через peer-роль). Причина та же, что в E1: round-robin voting на численных задачах хорошо работает только когда есть ≥3 правильных кандидата (`consensus_threshold = 3`); на dabench Cerebras-pool часто выдаёт разные численные ответы, и consensus просто не достигается. HITL-peer даёт критическую массу для consensus, но это патч, не решение.

### 8.2 Star + HITL «выглядит» лучше, чем в E1, но это артефакт top-3-фильтра

См. §6. **Замечание для текста диплома:** при сравнении E2 vs E1 необходимо всегда явно фиксировать subset задач — иначе легко прийти к ложному «HITL улучшает star в 1.4 раза».

### 8.3 Failed cells = 0

Подтверждено: `df['status'].value_counts()` → `completed: 2295`. Все ячейки финишировали через `finish_reason = success`. Это лучший результат среди всех экспериментов, что соответствует commit-сообщению.

### 8.4 Несбалансированный дизайн

В E2 `n` per (role, topology) меняется от 45 (mesh × *) до 135 (chain / debate / hierarchical × не-peer-роли). Это не баг, а следствие сочетания (а) per-task top-3 фильтра и (б) исключения 3 пар (§2.2). Для статистических тестов (ANOVA, paired-t) это означает:
- 2-way ANOVA на role × topology с unbalanced design — допустима, но требует Type III SS;
- per-task ранжирование ролей — балансное (на каждый task все роли имеют одинаковую `n` per topology), поэтому надёжнее.

### 8.5 Persona-seed одинаков для всех ролей

HITL-симулятор использует один и тот же `cerebras` (точнее `openai:gpt-4.1-mini`) с фиксированной persona-разметкой по ролям. Эффект «разной личности» не разделён от эффекта «разной семантики роли». В E5 это разделится за счёт реальных участников; в E2 — ограничение по дизайну.

### 8.6 Wall-time per cell vs end-to-end

End-to-end wall = 13.92 ч; суммарный CPU-time (`sum(wall_time_s)`) = 310.9 ч → эффективный parallelism = 22.3 (при заявленном `parallelism: 30` — небольшой простой из-за хвостов dabench).

## 9. Стоимость и время

| Категория | E2 | E1 (apples-restricted, 540 cells) |
|---|---:|---:|
| n | 2 295 | 540 |
| total cost | **$42.37** | $8.08 |
| mean cost per cell | $0.0185 | $0.0150 |
| mean iterations | 4.05 | 3.75 |
| mean wall_time, s | 487.7 | — |

**HITL overhead.** Per-cell HITL надбавка ≈ $0.0035 (+23%) по сравнению с тем же ячейкам E1 без HITL. Это меньше теоретического «2×» из коммит-сообщения — потому что judge-stage уже был платным в E1, а HITL-вызов через `openai:gpt-4.1-mini` (дешёвая модель) добавляет всего 1–2 запроса на run. Iterations выросли на +0.30 / run — HITL добавляет ровно один extra-step в трети случаев.

**Лифт-on-доллар.** За дополнительные $34 ($42.37 − $8.08) получено +3.3 п.п. среднего качества → ≈ $1 / 0.001 п.п. — соизмеримо с дешёвыми interventions. Для тех клеток, где лифт ≥ 5 п.п. (mesh × dabench, hierarchical × commongen, chain × dabench), HITL экономически оправдан; для star × verifiable — нет.

**Wall-time per cell** 487 с (≈ 8 мин) против ~150 с (≈ 2.5 мин) в E1: HITL-gateway добавляет блокирующий вызов с `timeout_s = 900`, что бьёт по «хвостам» — медианный wall_time остаётся низким (181–301 с per role), но среднее раздувается медленными случаями.

## 10. Связь со следующими экспериментами

**E3 (Adaptive topology, fixed role per task).** Получает от E2 таблицу `best_role_per_task` (§5):

```yaml
role_table:
  humaneval: coordinator
  gsm8k:     monitor
  commongen: peer
  dabench:   peer
```

Это **per-task-default role** для всех режимов `topology_router` (rule / llm / oracle). Без этого defaults E3 будет смешивать эффект «адаптивной топологии» с «случайно выбранной роли».

**E4 (Adaptive role).** Гипотезы, заточенные E2:
1. `role_fixed_best` (роль из таблицы выше) — нижний baseline.
2. `role_by_phase_rule` — для humaneval / gsm8k плохо: победитель `coordinator` / `monitor` уже почти полностью покрывает «фазу планирования / верификации»; ожидаемого прироста мало. Для commongen / dabench — большой потенциал, т.к. peer хорош в одной фазе, но в другой может быть избыточен.
3. `role_by_phase_llm` — окупаемость должна оцениваться против `router_cost_share` (как в E3).

**Confirmation на zai-glm-4.7 / gpt-4o.** Должен подтвердить, что **peer wins on creative/decision** — не артефакт gpt-oss-120b; и что **star + HITL** не даёт лифта — не артефакт «слабой основной модели» (если frontier-модель + HITL покажет лифт, это будет интересный contrasting result для текста).

**Что E2 не решает и должно перейти в E5 / limitations.**
- Реальный человек ≠ LLM-simulator (валидность);
- Persona-seed эффекты не отделены от role-семантики;
- DABench-склонность peer'а — артефакт top-3 фильтра (mesh / debate доступны только там) или универсальное свойство — не проверено.
