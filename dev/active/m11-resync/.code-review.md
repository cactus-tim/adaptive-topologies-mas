The bulk of the resync was executed faithfully: M10 merge with `resolve_spec` re-added, ground_truth dispatch via `_DEPS`, persist_tlx writer, model_version_snapshot capture, sandbox digest capture, GSM8K e2e replacement, and CI workflow are all in place and pass the full quality gate (1233 tests, mypy strict, ruff, alembic round-trip clean). ## Findings

### 1. Missing structlog bootstrap in `src/atm/__init__.py` (Step 2.2 not fully landed)
- **Severity**: major
- **File**: `src/atm/__init__.py:1-9`
- **Reference**: plan Step 2.2 ("wire bootstrap with `ATM_DISABLE_STRUCTLOG_BOOTSTRAP=1` opt-out"); plan Key Files Affected: "`src/atm/__init__.py` Extend — Bootstrap structlog with filter_secrets (opt-out via env var)"
- **Issue**: `src/atm/__init__.py` only re-exports `EVALUATORS, TASKS`; it does not import `configure_structlog` and does not gate a bootstrap call on `ATM_DISABLE_STRUCTLOG_BOOTSTRAP`. The library never actually configures structlog at import time.
- **Expected**: On `import atm`, if `os.environ.get("ATM_DISABLE_STRUCTLOG_BOOTSTRAP") != "1"`, call `atm.observability.log_processors.configure_structlog()`. Wrap in a narrow guard so a misconfigured downstream cannot block import (per the user's focus area #5, prefer `except (ImportError, ValueError)` rather than bare `except Exception: pass` — but the immediate gap is that no try/except exists at all because no call exists).
- **Actual**: No bootstrap is performed. `filter_secrets` is therefore not wired into structlog by default; downstream apps logging via the library's `structlog.get_logger(...)` will not redact secrets unless they configure structlog themselves.
- **Suggested Fix**: Append to `src/atm/__init__.py`:
  ```python
  import os
  if os.environ.get("ATM_DISABLE_STRUCTLOG_BOOTSTRAP") != "1":
      try:
          from atm.observability.log_processors import configure_structlog
          configure_structlog()
      except (ImportError, ValueError):
          pass
  ```
  Use a narrow exception list (not bare `Exception`) so genuine bugs surface.

### 2. `test_bootstrap_disabled_by_env` is a false-positive (does not test what it claims)
- **Severity**: major
- **File**: `tests/unit/observability/test_log_processors.py:213-227`
- **Reference**: plan Step 2.2 acceptance ("opt-out env var respected")
- **Issue**: The test patches `atm.observability.log_processors.configure_structlog`, sets the env var, reloads `atm`, and asserts the mock was not called. Because `atm/__init__.py` does not import or call `configure_structlog` AT ALL, the assertion trivially passes whether the env var is set or not — the test cannot distinguish the bootstrap-disabled path from the bootstrap-missing path.
- **Expected**: Once the bootstrap is added (Finding 1), the test should also include a positive control: with the env var unset, reloading `atm` must call `configure_structlog` exactly once.
- **Actual**: `test_bootstrap_enabled_by_default` (lines 230-247) does not actually reload `atm` — it just reproduces the env-gating logic inline and calls `configure_structlog()` itself, then asserts the mock was called. This is testing the test author's own glue, not the production bootstrap. Both tests give green-light coverage for code that does not exist.
- **Suggested Fix**: After implementing Finding 1, replace `test_bootstrap_enabled_by_default` with a real reload of `atm` (analogous to `test_bootstrap_disabled_by_env`) and assert `mock_cfg.assert_called_once()`. Keep the disabled-by-env test as-is — it will then meaningfully prove the env-gate works.

- **Actual**: The decision lives only in a git commit message; `m11-resync-context.md` still says "outer `docker.from_env()` also wrapped in `except (DockerException, OSError)`" while the code does not.

### 4. `conf/tools_policy.yaml` per_role keys are PascalCase but runner uses lowercase role names
- **Severity**: minor
- **File**: `conf/tools_policy.yaml:9-21`; consumer-side reference `src/atm/experiment/runner.py:332` and `src/atm/experiment/runner.py:410` (`roles = ["planner", "executor", "critic", "researcher"]`)
- **Reference**: plan Step 2.3 acceptance ("happy path per role"); arch.md §5.3
- **Issue**: The YAML uses `Planner`, `Executor`, `Critic`, `Researcher` (capitalized), and the unit tests in `tests/unit/tools/test_tools_policy.py` mirror that. However, every other role-keyed structure in the codebase (`runner._build_llm_wrappers`, `_build_agents`, `cfg.model.by_role`) uses lowercase (`"planner"`, `"executor"`, etc.). The moment a caller wires `ToolRegistry.tools_for(role)` into agent construction, it will get `[]` (just the global list) for every role unless the caller capitalizes the role string first.
- **Expected**: Match the role casing used everywhere else (`planner`, `executor`, `critic`, `researcher`). The current PascalCase form is a latent footgun that will silently degrade to "global tools only" when production wiring lands.
- **Actual**: PascalCase keys; tests prove the lookup works only if you happen to pass the same casing.
- **Suggested Fix**: Lowercase the keys in `conf/tools_policy.yaml` (`planner`, `executor`, `critic`, `researcher`); the unit tests use `tmp_path` fixtures with their own keys so most won't break, but adjust the few that explicitly load the project-root policy if any. Alternatively, normalize casing inside `tools_for()` (e.g. `role.lower()`), but that is more invasive.

### 5. `runner.run_one` finally-block UPDATEs bypass `session_scope` and use bare commit
- **Severity**: minor
- **File**: `src/atm/experiment/runner.py:760-803`
- **Reference**: plan Steps 3.2 / 3.3 ("UPDATE … in `finally` block")
- **Issue**: The model_version_snapshot and sandbox_image_digest UPDATEs are wrapped in `async with session_factory() as _snap_session:` with manual `_snap_session.execute(...)` + `await _snap_session.commit()`. The rest of the runner uses `session_scope(session_factory)` which provides commit-on-success / rollback-on-error semantics. The bare-context pattern works (the outer `try/except _snap_exc` swallows failures and logs), but it is a stylistic divergence from the rest of the file and skips the rollback path. Idempotency is fine because both UPDATEs are pure value-overwrites (no INSERTs, no FK additions).
- **Expected**: Use `session_scope(session_factory)` for consistency, or document why the bare context is preferred (e.g. to avoid raising on commit-time conflicts in the finally block).
- **Actual**: Bare context with manual commit; works, but inconsistent.
- **Suggested Fix**: Refactor to `async with session_scope(session_factory) as _snap_session:` and drop the manual `commit()`. The outer `try/except _snap_exc` already provides the swallow-and-log behavior the finally block needs.

### 6. `runner.run_one` truncates `sandbox.image_digest` to `[:80]` defensively
- **Severity**: minor
- **File**: `src/atm/experiment/runner.py:794`
- **Reference**: plan Step 6 / Step 3.3 ("Capture only `image_map["python"]` digest into single-string column"); schema column is `String(80)` (`src/atm/storage/models.py:153`, alembic `0001`).
- **Issue**: A docker-py image id is always `sha256:` + 64 hex chars = 71 characters, comfortably under 80. The `[:80]` slice is harmless but adds the false impression that overflow is expected. If a future digest ever DOES exceed 80 (e.g. SHA512), the truncate would silently corrupt the persisted value rather than surface the bug.
- **Expected**: Either drop the truncate (let asyncpg raise `StringDataRightTruncation` if the column ever overflows — surfacing the schema mismatch loudly), or keep the truncate AND log a warning when the input length actually exceeds 80.
- **Actual**: Silent truncate to 80.
- **Suggested Fix**: Replace `values(sandbox_image_digest=_sandbox_digest[:80])` with either (a) `values(sandbox_image_digest=_sandbox_digest)` and rely on the column constraint, or (b) add `if len(_sandbox_digest) > 80: logger.warning("sandbox_image_digest exceeds column width", length=len(_sandbox_digest))` immediately before the slice. Option (a) is simpler given the digest is always 71 chars.

### 7. `persist_tlx` calls `await session.commit()` even though callers wrap in `session_scope`
- **Severity**: minor
- **File**: `src/atm/evaluation/tlx.py:75`
- **Reference**: plan Step 2.4 ("idempotent UPDATE writer; mirror style of evaluation/aggregator.py::persist_quality")
- **Issue**: `persist_tlx` calls `await session.commit()` at the end. Integration test `tests/integration/evaluation/test_tlx_persist.py` wraps the call in `async with session_scope(factory) as session:` which itself commits on clean exit. The result is two commits per call (the second is a no-op SQLAlchemy-side, but it is wasted bookkeeping). `persist_quality` follows the same pattern (also commits internally) so the `mirror style of persist_quality` directive is satisfied; the inconsistency is upstream of this PR.
- **Expected**: A writer helper either (a) commits internally and is called outside `session_scope`, or (b) does not commit and is called inside `session_scope`. Mixing both is harmless but confusing.
- **Actual**: Internal commit + external `session_scope` commit; functionally correct, idempotent, but redundant.
- **Suggested Fix**: Either drop the internal commit (and document that the caller must scope the transaction) — preferred for symmetry with the M11 aggregator pattern — or keep it and remove the `session_scope` wrap from the integration test. No production behavior change either way.
