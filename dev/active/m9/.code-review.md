# Code Review: M9 — Human Gateway + LLM-simulator (HITL infrastructure)

## Mode
full

## Verdict
FINDINGS

## Summary
План в основном реализован: модуль `atm.human` создан, миграция корректна, callback расширен двумя event-handler'ами, HumanCfg добавлен в ExperimentConfig, Chain получил условную вставку human_reviewer. Тесты unit зелёные.

Однако обнаружены критические дефекты на границе **dispatch → callback** и в конфигурации по умолчанию, которые гарантированно сломают любой реальный run с `human.enabled=True`:

1. **Контрактный mismatch ключей в payload** между `human_reviewer` node и `_handle_human_request/_handle_human_response` — ни одна запись в `human_interactions` не будет сделана (KeyError swallowed). Идемпотентность и единственный writer (§10.2) фактически не работают на интеграционном уровне.
2. **Default-конфигурация падает с ValueError**: `timeout_policy="llm_fallback"` + `llm_fallback_gateway=None` хардкод в chain.py.
3. **LLMSimulatedGateway создаётся с llm=None в Runner** — крэш на первом ainvoke.

Эти дефекты не покрыты unit-тестами потому что: (a) chain-тесты проверяют только что event был dispatched, но не payload-ключи; (b) тесты chain используют `timeout_s=None`, минуя ветку с `request_with_timeout`; (c) тесты chain мокают `LLMSimulatedGateway`.

## Findings

### F1 — Контрактный mismatch: human_request payload keys
- **Severity**: critical
- **File**: `src/atm/topology/chain.py:182-188` vs `src/atm/observability/callbacks.py:497-505`
- **Reference**: plan Step 5 (Callback — единственный writer), arch.md §10.2
- **Issue**: Узел dispatch'ит `{"request_id": request_id, "ctx": ctx.model_dump(mode="json")}`. Callback ожидает в `_handle_human_request`:
  - `data["run_id"]` — отсутствует в payload (KeyError)
  - `data["role"]` — отсутствует (находится внутри `ctx`)
  - `data.get("context_json", {})` — chain дал ключ `"ctx"`, не `"context_json"`
- **Expected**: payload должен содержать `run_id`, `request_id`, `role`, `context_json`, `requested_at` (как в `_human_request_data` в tests/unit/observability/test_callbacks_human.py).
- **Actual**: KeyError на `data["run_id"]` ловится `except Exception` блоком и логируется как error; INSERT не выполняется. На PG ни одной записи в `human_interactions` не появится при реальном запуске.
- **Suggested Fix**: В `chain.py` _build_human_reviewer_node изменить dispatch на:
  ```python
  await adispatch_custom_event("human_request", {
      "run_id": run_id,
      "request_id": request_id,
      "role": str(human_cfg.role),
      "context_json": ctx.model_dump(mode="json"),
      "requested_at": datetime.now(UTC),
  })
  ```
  Либо привести callback к чтению из nested `ctx` — но согласовать с тестом `test_callbacks_human.py` (там используется первый вариант).

### F2 — Контрактный mismatch: human_response payload keys
- **Severity**: critical
- **File**: `src/atm/topology/chain.py:209-216` vs `src/atm/observability/callbacks.py:529-549`
- **Reference**: plan Step 5
- **Issue**: Узел dispatch'ит `{"request_id": request_id, "response": response.model_dump(mode="json")}`. Callback читает:
  - `data["run_id"]` — отсутствует (KeyError)
  - `data["request_id"]` — OK
  - `data.get("response_json", {})` — chain дал ключ `"response"`, не `"response_json"`
  - `data.get("answered_at", ...)`, `data.get("source"...)`, `data.get("timed_out"...)`, `data.get("latency_s")` — отсутствуют
- **Expected**: payload должен содержать `run_id`, `request_id`, `answered_at`, `response_json`, `source`, `timed_out`, `latency_s` (как в `_human_response_data` в test_callbacks_human.py).
- **Actual**: KeyError на `data["run_id"]` ловится `except Exception`; UPDATE не выполняется; `response_json` остаётся NULL.
- **Suggested Fix**: 
  ```python
  await adispatch_custom_event("human_response", {
      "run_id": run_id,
      "request_id": request_id,
      "answered_at": datetime.now(UTC),
      "response_json": response.model_dump(mode="json"),
      "source": response.source,
      "timed_out": response.timed_out,
      "latency_s": <measured>,
  })
  ```

### F3 — Default-конфиг падает: llm_fallback policy без fallback gateway
- **Severity**: critical
- **File**: `src/atm/topology/chain.py:196-204`, `conf/human/llm_simulated.yaml:5`
- **Reference**: plan Step 7 (timeout wrapper)
- **Issue**: `chain.py` всегда передаёт `llm_fallback_gateway=None`. `HumanCfg.timeout_policy` по умолчанию `"llm_fallback"` (config.py:135), и `conf/human/llm_simulated.yaml` тоже использует `llm_fallback`. `request_with_timeout` валидирует это eagerly и бросает `ValueError`:
  ```python
  if policy == "llm_fallback" and llm_fallback_gateway is None:
      raise ValueError(...)
  ```
  Любой реальный запуск с default-конфигом упадёт ещё до первого таймаута.
- **Expected**: либо построить и передать fallback gateway (например, LLMSimulatedGateway), либо при `policy=='llm_fallback'` без fallback-LLM граmotно деградировать в `skip`.
- **Actual**: гарантированный ValueError при `timeout_s>0` + дефолтном `timeout_policy`.
- **Suggested Fix**: В chain.py build(), когда `human_cfg.timeout_policy == "llm_fallback"`, конструировать дополнительный LLMSimulatedGateway-instance (или переиспользовать тот же primary, если он llm_simulated) и пробросить его как `llm_fallback_gateway` в node-фабрику. Альтернатива: изменить дефолт в `HumanCfg.timeout_policy` на `"skip"` (но это меняет план).

### F4 — LLMSimulatedGateway создаётся с llm=None
- **Severity**: critical
- **File**: `src/atm/topology/chain.py:451-460`, `src/atm/experiment/runner.py:542-547`
- **Reference**: plan Step 8 (Runner — human_cfg kwarg в topology.build)
- **Issue**: `chain.py` читает `gateway_llm = kwargs.get("human_gateway_llm")` и передаёт `LLMSimulatedGateway(llm=gateway_llm)`. Runner НЕ передаёт `human_gateway_llm` (см. runner.py:542-547, kwargs только `checkpointer` и `human_cfg`). Значит `gateway_llm=None`, конструируется `LLMSimulatedGateway(llm=None)`, и при первом `await self._llm.ainvoke(...)` (`llm_simulated.py:116`) — AttributeError.
- **Expected**: Runner должен собрать отдельный `LLMWrapper` для модели `cfg.human.model` (или дефолтной) и передать как `human_gateway_llm`.
- **Actual**: AttributeError на первом вызове human_reviewer; run падает.
- **Suggested Fix**: В `runner.py::run_one` после построения `llms` добавить:
  ```python
  human_llm = None
  if cfg.human is not None and cfg.human.enabled and cfg.human.gateway == "llm_simulated":
      model_id = cfg.human.model or cfg.model.default
      human_llm = build_llm(model_id=model_id, pricing=pricing, budget=budget)
  ```
  и передать `human_gateway_llm=human_llm` в `topology.build(...)`. Также подумать, как тестировать это в unit (с FakeLLM-fixture).

### F5 — run_with_human обходит callback writer (§10.2 violation для interrupt-path)
- **Severity**: major
- **File**: `src/atm/human/runner.py:214`
- **Reference**: plan Step 10 (Orchestration helper), arch.md §10.2 (callback — единственный writer)
- **Issue**: `run_with_human` вызывает `gateway.request(ctx, request_id=...)` напрямую и НЕ dispatch'ит `human_request` / `human_response` события. Если в M14+ начнёт использоваться real `interrupt()`-path, каждый запрос будет проходить мимо `ExperimentCallbackHandler` — записи в `human_interactions` не создадутся.
- **Expected**: до и после `gateway.request` должен быть `adispatch_custom_event("human_request"/"human_response", ...)` — тот же контракт, что в chain.py node.
- **Actual**: helper резолвит interrupt'ы, но не пишет ни в parquet, ни в PG. M9 это пока не активирует (interrupt-path не используется в Chain), однако helper уже включён в публичный API и комментарий в docstring (`Current M9 scope ... helper is therefore "no-op" for existing Chain HITL runs`) подтверждает, что dispatch отсутствует намеренно.
- **Suggested Fix**: добавить dispatch перед и после `gateway.request`. Альтернативно: явно задокументировать в docstring, что caller должен установить callback-handler, который сам обрабатывает interrupt-резолюцию (но это размывает контракт single-writer).

### F6 — run_with_human обходит request_with_timeout
- **Severity**: major
- **File**: `src/atm/human/runner.py:214`
- **Reference**: plan Step 10 + focus area #2 (timeout/fallback policy at topology level)
- **Issue**: `run_with_human` зовёт `gateway.request(...)` без `request_with_timeout`. Если interrupt-path активируется, timeout/fallback policy будет не enforced. Чтобы реализовать паттерн «timeout at topology level», нужно сюда тоже добавить timeout-обёртку, передавая `timeout_s` и `policy` из вызывающего кода или payload'a.
- **Expected**: либо `run_with_human` принимает `timeout_s/policy/llm_fallback_gateway` и применяет `request_with_timeout`, либо это явно делегируется узлу, который вызвал `interrupt(payload)` — но тогда узел уже должен пройти через timeout-wrapper до interrupt'a, что архитектурно странно.
- **Actual**: timeout/fallback в interrupt-path вообще не работает.
- **Suggested Fix**: добавить параметры `timeout_s, timeout_policy, llm_fallback_gateway` в `run_with_human` и заменить прямой `gateway.request` на `request_with_timeout(...)`.

### F7 — Чувствительные fields `_ = source`/`_ = timed_out`/`_ = latency_s` — мёртвый код
- **Severity**: minor
- **File**: `src/atm/observability/callbacks.py:554-556`
- **Reference**: plan Step 5
- **Issue**: Код извлекает `source`, `timed_out`, `latency_s` из payload, затем сразу присваивает `_ = ...` с комментарием «used by caller via response_json». Это намеренная заглушка для будущего расширения, но логирования или валидации нет. Если payload не содержит этих полей (что фактически и происходит — см. F2), UPDATE отрабатывает с дефолтами без warning'а.
- **Expected**: либо использовать (логировать через self._log.debug с этими значениями), либо удалить блок до момента, когда будут добавлены реальные колонки.
- **Suggested Fix**: убрать `_ = ...` строки и переменные `source/timed_out/latency_s` пока что; либо логировать диагностически через `self._log.debug(...)`.

### F8 — `_route_from_critic` мутирует входной state in-place
- **Severity**: minor (long-standing, не новый в M9 — но усугубляется human_reviewer)
- **File**: `src/atm/topology/chain.py:341-345`
- **Reference**: existing pattern; не нарушает план, но стоит обратить внимание
- **Issue**: `shared = state["shared"]` (без deepcopy) → in-place мутация `iter_total` и `iteration`. В то же время `human_reviewer` делает `deepcopy(state.get("shared", {}))` и возвращает дельту. После HITL-вставки маршрут `human_reviewer → _route_from_critic` будет читать iter_total из state, увеличивать его, но human_reviewer уже вернул свою копию shared — порядок merge'ей в LangGraph должен быть последовательным, что предположительно работает, но архитектурно несогласованно.
- **Expected**: либо все node'ы возвращают immutable deltas (deepcopy + return), либо все мутируют — выбрать один стиль.
- **Suggested Fix**: вне scope M9. Отметить как technical debt; формальный исправление — separately.

### F9 — `LLMSimulatedGateway` lazy-import с `LLMSimulatedGateway = None` без noqa
- **Severity**: minor
- **File**: `src/atm/topology/chain.py:87-100`
- **Reference**: existing code; не критично
- **Issue**: Три блока `try/except ImportError → ... = None` для `LLMSimulatedGateway`, `CLIGateway`, `request_with_timeout`. Поскольку `atm.human` — собственный модуль того же пакета, ImportError здесь практически невозможен. Это создаёт избыточные `# type: ignore` и `is None` ветки, которые никогда не сработают.
- **Expected**: прямой импорт `from atm.human.llm_simulated import LLMSimulatedGateway`. Тесты, которые сейчас патчат `atm.topology.chain.LLMSimulatedGateway`, продолжат работать.
- **Suggested Fix**: заменить try/except на прямой `import`; удалить `is None` проверки (или превратить в `assert ... is not None`).

### F10 — Документация runner.py docstring неточна
- **Severity**: minor
- **File**: `src/atm/human/runner.py:8-17`
- **Reference**: plan Step 10
- **Issue**: Docstring пишет: «In M9, the Chain topology's human_reviewer node calls gateways synchronously inside the node (no LangGraph interrupt() call is made from that node). The helper is therefore "no-op" for existing Chain HITL runs». Это означает, что `run_with_human` в M9 фактически не задействован реальным потоком — он только тестируется через `FakeInterruptingGraph`. Если так, его экспорт из `atm.human.__init__` создаёт false-API контракт.
- **Expected**: либо `run_with_human` действительно используется (тогда Runner должен звать его вместо прямого `ainvoke`), либо его следует пометить как experimental/forward-compat и не экспортировать публично до M14.
- **Suggested Fix**: рассмотреть вызов `run_with_human(...)` из `runner.py::run_one` вместо `compiled_graph.ainvoke(...)` для случая `cfg.human is not None`. Либо явно пометить helper как private/forward-compat (префикс `_` или подкаталог `_forward/`).
