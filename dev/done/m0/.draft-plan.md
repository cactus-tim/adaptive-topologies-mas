# Implementation Plan: M0 — Bootstrap проекта

## Task Summary

Поднять рабочий скелет репозитория для дипломного фреймворка **Adaptive Topologies MAS**:
`uv`-проект на Python 3.11+, пустая структура каталогов по §4 PLAN.md, `docker-compose.yml` с Postgres 16, инициализированный Alembic (async-template) с пустой initial-миграцией, конфиги ruff/mypy, pytest-скелет с одним smoke-тестом, `.env.example`, `README.md` с quickstart-ом на русском.

Область M0 — сугубо scaffolding: **никакой бизнес-логики не пишется**. Цель — дать в руки последующим milestone'ам готовый чистый «стенд»: при `docker-compose up -d && uv run pytest` всё зелёное; `uv run ruff check .` без ошибок; `uv run mypy src/` без ошибок.

**Final Class**: standard

**Rationale**: задача механическая, но широкая — 7 подзадач, ~20 файлов, 14+ пустых пакетов с `__init__.py`, интеграция Alembic + async-template + docker-compose, конфиги нескольких инструментов (ruff, mypy, pytest, uv). INITIAL_CLASS=standard сохраняется; не trivial (слишком много артефактов и языковых точек проверки), не complex (нет бизнес-логики, алгоритмики, внешних интеграций сверх postgres container).

## Needs Integration Tests

**Decision**: no

**Rationale**: M0 — scaffolding без published contracts. Smoke-тест pytest (тривиальная проверка `1+1==2` или import пакета) уже включён в чеклист M0, и он играет роль sanity-check окружения, не acceptance-test контракта. Будущие published contracts (Postgres schema, CLI) появляются в M1/M3/M6 и будут покрываться отдельными интеграционными тестами тогда.

## Codebase Context

Репозиторий сейчас **greenfield** — в корне есть только:

- `dev/PLAN.md` (план milestone'ов, §4 содержит точную структуру каталогов, §5 — модель данных, §8 — M0 чеклист)
- `dev/arch.md` (архитектурный документ; §10.3 observability async-flush, §11.3 two-pool Postgres, §12.1 ModelCfg, §14.4 reproducibility bundle)
- `dev/active/m0/` — рабочая папка под этот milestone (сюда пишется `.draft-plan.md`)

Важные архитектурные факты, которые влияют на M0:

1. **Two connection pools** (arch.md §11.3). На M3 будут заведены **два** async-engine'а: один под `langgraph-checkpoint-postgres` (autocommit=True), другой под бизнес-SQLAlchemy. Alembic обслуживает **только** бизнес-миграции; checkpoint-таблицы создаёт `await checkpointer.setup()` на рантайме. → В M0: `.env.example` держит **один** `PG_DSN` (общий хост Postgres, два engine'а поднимутся из него в M3). Alembic-env.py пишет сразу под async-драйвер (asyncpg) — как только появятся модели в M3, он будет работать без доработок.

2. **Pydantic v2 + OmegaConf + TypedDict state** (arch.md §17, deviations #1, #5). На M0 зависимости не ставим, но слоты для них в `pyproject.toml` в опциональных группах / TODO-комментариях оставляем, чтобы последующие milestone'ы добавляли через `uv add` без структурной ломки.

3. **Reproducibility bundle** (arch.md §14.4). Переменные окружения, которые точно понадобятся во всей системе: `PG_DSN`, `DATA_DIR` (под parquet-выхлоп), `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`. На M0 → `.env.example` их перечисляет с пустыми значениями (не фактические ключи).

4. **Структура `src/atm/`** (PLAN.md §4) — 14 подкаталогов, все будут пусты или содержать только placeholder-`__init__.py` + редко `providers/`-подпакет; mypy strict **ломается на отсутствии `__init__.py`** в пакетах (namespace package issue с `mypy_path`), поэтому все пакеты инициализируем явно.

5. **Только Postgres в docker-compose** (чёткое указание координатора). Никаких Redis, Prometheus, Jaeger — они не в M0 чеклисте.

### Step 1: Инициализировать `uv`-проект и базовый `pyproject.toml`

**Type**: simple

**What**: запустить `uv init --bare --python 3.11` в корне репозитория, затем отредактировать сгенерированный `pyproject.toml`: задать `name="atm"`, `description` (English), `requires-python=">=3.11"`, `[tool.uv]` c `package = true`, добавить `[project]`-секцию с `version = "0.1.0"` и `[build-system]` под hatchling (uv-дефолт). **Зависимости (в `[project].dependencies`) пока пустые** — они добавляются по мере M1+. Добавить `[tool.uv.sources]` пустую (placeholder). Настроить структуру src-layout: `[tool.hatch.build.targets.wheel] packages = ["src/atm"]`.

**Files / Components**:
- `pyproject.toml` (создаётся)
- `uv.lock` (будет сгенерирован автоматически на первом `uv sync`, но в этом шаге не принципиален)
- `.python-version` (uv создаёт; фиксирует 3.11)

**Depends On**: none

**Can-Parallel-With**: 2, 5, 7

**Skills**: `python.md` (если есть в `.claude/skills/`)

**Assumptions**: `uv` установлен; `uv init --bare` не конфликтует с уже существующими dev-файлами (он только создаёт `pyproject.toml`, `.python-version`, `.gitignore` — но если `.gitignore` уже есть, uv её не перезатирает; мы потом объединяем).

**Implementation Notes**:
- Команда: `uv init --bare --python 3.11` (флаг `--bare` — минимальный `pyproject.toml` без sample-кода, см. [uv migrate from requirements.txt](https://pydevtools.com/handbook/how-to/migrate-requirements.txt/)).
- Актуальная `uv` по состоянию на апрель 2026 — версии 0.5.x/0.6.x; синтаксис `[dependency-groups]` (PEP 735) поддерживается нативно, это **predzateленный** формат для dev-зависимостей вместо устаревшего `[tool.uv.dev-dependencies]` (см. [uv docs: managing dependencies](https://docs.astral.sh/uv/concepts/projects/dependencies/)).
- `pyproject.toml` должен содержать англоязычное `description = "Adaptive Topologies MAS — framework for experiments with adaptive multi-agent LLM topologies with HITL."`.
- Content example (English-only):
  ```toml

  name = "atm"
  version = "0.1.0"
  description = "Adaptive Topologies MAS — framework for experiments with adaptive multi-agent LLM topologies with HITL."
  readme = "README.md"
  requires-python = ">=3.11"
  dependencies = []

  [build-system]
  requires = ["hatchling"]
  build-backend = "hatchling.build"

  [tool.hatch.build.targets.wheel]
  packages = ["src/atm"]
  ```
- **Не добавлять** в M0 тяжёлые runtime-зависимости (`langgraph`, `langchain-*`, `pyarrow`, `pandas`, `matplotlib`, `jupyter`, `langgraph-checkpoint-postgres`). Они приходят в M1–M8.
- Dev/test зависимости добавляются в отдельном Step 3 командой `uv add --group ...`.

**Expected Outcome**: в корне репозитория есть `pyproject.toml` с минимальной корректной структурой, Python 3.11+ зафиксирован, пакет `atm` прописан как src-layout. Никаких runtime-deps пока нет.

**Verification**: `uv sync` проходит без ошибок; `uv run python -c "print('ok')"` выводит `ok`.

**Risks**: 
- Если `.gitignore` уже существовал — `uv init` может его пропустить; мы в Step 7 создаём/дополняем `.gitignore` явно.
- Если пользователь однажды запускал `uv init` — повторный вызов ругнётся. Мigitация: проверить наличие `pyproject.toml` до запуска; если есть — пропустить `init`, сразу править вручную.

**Rollback**: `rm pyproject.toml .python-version uv.lock` и повторить.

### Step 3: Добавить dev/test dependency groups через `uv add --group dev/test ...`

**Type**: simple

**What**: добавить инструменты разработки через uv dependency groups (PEP 735). Две группы: `dev` (линтеры, типы, форматтеры, alembic + минимальный runtime под async-alembic) и `test` (pytest и plugins). В `[dependency-groups].dev` включить ссылку на `test` группу. В M0 ставим сами инструменты **плюс** `sqlalchemy[asyncio]>=2.0` и `asyncpg>=0.29` — минимальный набор, необходимый для работоспособного async-alembic env.py.

**Files / Components**:
- `pyproject.toml` (дополняется секцией `[dependency-groups]`)
- `uv.lock` (обновляется)

**Depends On**: 1 (нужен валидный pyproject.toml)

**Can-Parallel-With**: none (пишет в `pyproject.toml`, сериализуется относительно Step 4/6/8)

**Skills**: `python.md`

**Assumptions**: версии, проверенные на момент планирования (апрель 2026):
- `ruff >= 0.9` (стабильная линия; актуальная 2026)
- `mypy >= 1.14` (поддержка PEP 695, актуальная 2026)
- `pytest >= 8.3` (поддерживает asyncio_mode auto)
- `pytest-asyncio >= 0.25` (новый API; версии 0.25–1.x сохраняют совместимость с asyncio_mode auto; см. [pytest-asyncio changelog](https://pytest-asyncio.readthedocs.io/en/stable/reference/changelog.html))
- `alembic >= 1.13` (async template stable)
- `sqlalchemy[asyncio] >= 2.0` (требуется async-шаблоном alembic: `from sqlalchemy.ext.asyncio import async_engine_from_config`)
- `asyncpg >= 0.29` (async-драйвер для Postgres; без него `postgresql+asyncpg://...` DSN не резолвится)

**Implementation Notes**:
- Команды:
  ```bash
  uv add --group dev ruff mypy alembic 'sqlalchemy[asyncio]>=2.0' 'asyncpg>=0.29'
  uv add --group test pytest pytest-asyncio
  ```
- **Почему sqlalchemy+asyncpg уже на M0**: `alembic init -t async` генерирует `alembic/env.py` с `from sqlalchemy.ext.asyncio import async_engine_from_config, AsyncEngine`. Exit-criteria Step 6 требует успешного `uv run alembic upgrade head` на поднятом Postgres — без этих двух пакетов команда падает на `ImportError`/`ModuleNotFoundError`. Это минимально необходимый набор, **не** фичерный.
- **Что в M0 по-прежнему НЕ добавляем** (придёт в M1–M8): `langgraph`, `langchain-*`, `langgraph-checkpoint-postgres`, `pyarrow`, `pandas`, `matplotlib`, `jupyter`. Они не нужны для scaffolding и тянут лишний вес.
- Формат в `pyproject.toml`:
  ```toml
  [dependency-groups]
  dev = [
      "ruff>=0.9",
      "mypy>=1.14",
      "alembic>=1.13",
      "sqlalchemy[asyncio]>=2.0",
      "asyncpg>=0.29",
      {include-group = "test"},
  ]
  test = [
      "pytest>=8.3",
      "pytest-asyncio>=0.25",
  ]
  ```
- `uv sync` включает группу `dev` по умолчанию (см. [uv docs: dependency groups](https://docs.astral.sh/uv/concepts/projects/dependencies/)), так что все tools будут доступны через `uv run ...`.
- Отсутствие верхних границ версий (`<N`) — осознанный выбор на M0 (community-best-practice). Зафиксируется по факту первого breaking-change инцидента.

**Expected Outcome**: `uv.lock` содержит ruff/mypy/alembic/pytest/pytest-asyncio/sqlalchemy/asyncpg и их транзитивные deps. `uv run ruff --version`, `uv run mypy --version`, `uv run pytest --version`, `uv run alembic --version` все отвечают. `python -c "import sqlalchemy.ext.asyncio; import asyncpg"` работает.

**Verification**:
```bash
uv sync --group dev              # успешно собирает sqlalchemy[asyncio] + asyncpg
uv run ruff --version            # ≥ 0.9
uv run mypy --version            # ≥ 1.14
uv run pytest --version          # ≥ 8.3
uv run alembic --version         # ≥ 1.13
uv run python -c "import sqlalchemy.ext.asyncio, asyncpg; print('ok')"   # ok
```

**Risks**:
- Если решим повышать нижнюю границу mypy (например, до >=1.15, >=1.16) — проверить, что на дату dev-runtime нет breaking changes в config-формате.
- pytest-asyncio 1.x подтянулся в ноябре 2025 — deprecation для старого `asyncio_mode='legacy'`, но `auto` работает и в 0.x и в 1.x. Спецификатор `>=0.25` безопасен.
- `asyncpg` — C-extension пакет, на редких платформах сборка wheel'а может не найти prebuilt — uv 0.5+ умеет падать с понятной ошибкой, на стандартных linux/macOS всё ок.

**Rollback**: `uv remove --group dev ruff mypy alembic sqlalchemy asyncpg && uv remove --group test pytest pytest-asyncio`.

### Step 4: Настроить конфиги `ruff` и `mypy` в `pyproject.toml`

**Type**: simple

**What**: в `pyproject.toml` прописать `[tool.ruff]`, `[tool.ruff.lint]`, `[tool.ruff.format]`, `[tool.mypy]` секции. Ruff: `target-version = "py311"`, `line-length = 100`, включить набор правил `E, W, F, I, UP, B, SIM, C4, N, RUF` (базовый backend-ориентированный профиль). Mypy: `python_version = "3.11"`, `strict = true`, `warn_unused_ignores = true`, `mypy_path = ["src"]`, `packages = ["atm"]`, `files = ["src/atm"]`. Область `files = ["src/atm"]` сознательно исключает `alembic/` из mypy-сканирования (см. Implementation Notes).

**Files / Components**:
- `pyproject.toml` (добавляются секции `[tool.ruff]`, `[tool.ruff.lint]`, `[tool.ruff.format]`, `[tool.mypy]`)

**Depends On**: 3 (нужен pyproject.toml с dev-группой)

**Can-Parallel-With**: none (пишет в `pyproject.toml`, сериализуется относительно Step 3/6/8)

**Skills**: `python.md`

**Assumptions**: код на M0 — почти пустые `__init__.py`; mypy strict проходит на пустых пакетах без единого warning (см. §17 arch.md deviation #1 — TypedDict-first правило; это не для M0, это позже).

**Implementation Notes**:
- Актуальные ruff-правила 2026 описаны в [Ruff configuration docs](https://docs.astral.sh/ruff/configuration/). Набор `E,W,F,I,UP,B,SIM,C4,N,RUF` — классика; `ANN` (аннотации типов) оставляем на усмотрение mypy — ruff ANN даёт много шума на пустых `__init__.py`.
- `tool.ruff.lint.extend-select = ["I"]` для сортировки импортов.
- `tool.ruff.format` — ставим по дефолту (double-quote, Python 3.11 targets). Line-length 100 как разумный компромисс (в community 88 или 100; проект средний).
- `tool.mypy.strict = true` — покрывает `disallow_untyped_defs`, `disallow_any_generics`, `warn_return_any`, `no_implicit_optional` и пр. Но на M0 все функции в пакетах — пустые `__init__.py`, и strict-mypy их **пропустит** (там нет функций), поэтому ожидаем 0 ошибок.
- `mypy_path = ["src"]` — критично для src-layout, иначе mypy не находит пакеты.
- **Про alembic и mypy**: `files = ["src/atm"]` сознательно **исключает** `alembic/` из mypy-сканирования. Альтернативой был бы `[[tool.mypy.overrides]] module = ["alembic.*"] ignore_errors = true`, но явное `files`-ограничение проще и прозрачнее. Зафиксировано здесь как осознанное решение.
- Содержимое (English, компактно):
  ```toml
  [tool.ruff]
  target-version = "py311"
  line-length = 100
  src = ["src", "tests"]

  [tool.ruff.lint]
  select = ["E", "W", "F", "I", "UP", "B", "SIM", "C4", "N", "RUF"]
  ignore = ["E501"]  # line-length enforced by formatter

  [tool.ruff.format]
  quote-style = "double"
  indent-style = "space"

  [tool.mypy]
  python_version = "3.11"
  strict = true
  warn_unused_ignores = true
  warn_redundant_casts = true
  mypy_path = ["src"]
  files = ["src/atm"]   # NB: intentionally excludes alembic/ from type-checking
  namespace_packages = true
  explicit_package_bases = true

  [[tool.mypy.overrides]]
  module = ["tests.*"]
  disallow_untyped_defs = false  # тесты не обязаны иметь полную типизацию
  ```
- Проверить, что конфиги не ломаются на Step 2 структуре: `uv run ruff check .` = exit 0; `uv run mypy src/` = exit 0 (нет .py с логикой).
- Команды для developer-агента: после записи — запустить `uv run ruff check .` и `uv run mypy src/`. Оба должны пройти.

**Expected Outcome**: конфиги ruff/mypy работают на пустых пакетах без ошибок.

**Verification**:
```bash
uv run ruff check .           # exit 0, "All checks passed!"
uv run ruff format --check .  # exit 0
uv run mypy src/              # "Success: no issues found in N source files"
```

**Risks**:
- mypy при namespace packages может выдать `duplicate module` ошибку, если dir-структура несвета. Fix: `namespace_packages = true` + `explicit_package_bases = true` (оба выставлены).
- Какая-нибудь правилка из `RUF` сработает на docstring в `__init__.py` — маловероятно, но если случится — добавить в `ignore` нужное.

**Rollback**: удалить добавленные секции из `pyproject.toml`.

### Step 5: Создать `docker-compose.yml` с Postgres 16

**Type**: simple

**What**: создать в корне `docker-compose.yml` с единственным сервисом `postgres` (image `postgres:16-alpine`), именованным volume `atm_postgres_data`, healthcheck через `pg_isready`, проброс порта 5432 на хост, env-переменные `POSTGRES_USER/PASSWORD/DB` берутся из `.env` (фолбек-значения для dev — указаны прямо в compose, но реальные перекрываются из `.env`).

**Files / Components**:
- `docker-compose.yml` (создаётся)

**Depends On**: none (этот шаг независим от pyproject)

**Can-Parallel-With**: 1, 2, 7

**Skills**: `docker.md` (если есть в `.claude/skills/`), `python.md` (обзорно)

**Assumptions**: docker-compose V2 (`docker compose up -d`). Хост-порт 5432 свободен; если у пользователя уже крутится локальный Postgres — он мапнётся на `5433` или пользователь остановит свой. Дефолт — 5432 как в `PG_DSN` в `.env.example`.

**Implementation Notes**:
- Образ `postgres:16-alpine` — меньше, faster pull (арх-документ не требует specific feature вне обычного Postgres 16).
- Healthcheck pattern: `pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}` с `interval: 5s`, `timeout: 5s`, `retries: 10`, `start_period: 10s` (подсмотрено в [peter-evans/docker-compose-healthcheck](https://github.com/peter-evans/docker-compose-healthcheck) и [oneuptime PostgreSQL Docker Compose 2026 guide](https://oneuptime.com/blog/post/2026-01-21-postgresql-docker-compose/view)).
- Named volume: `atm_postgres_data` на `/var/lib/postgresql/data`.
- `POSTGRES_USER=atm`, `POSTGRES_PASSWORD=atm`, `POSTGRES_DB=atm` как defaults для dev; переопределяются `.env`.
- Не писать `version: "3.8"` в compose — в V2 ключ deprecated (предупреждение об этом — обычное дело в 2026, многие гайды его убирают).
- Не включаем `depends_on` / app-сервис — в M0 приложения ещё нет, compose поднимает только Postgres.
- Содержимое (English, без комментариев-излишеств, но с docstring-блоком вверху):
  ```yaml
  # docker-compose.yml
  # Postgres 16 for atm (Adaptive Topologies MAS).
  # Used by SQLAlchemy async engine (business data) and by
  # langgraph-checkpoint-postgres (graph checkpoints) — both engines
  # connect to the same physical instance, see arch.md §11.3.

  services:
    postgres:
      image: postgres:16-alpine
      container_name: atm_postgres
      restart: unless-stopped
      environment:
        POSTGRES_USER: ${POSTGRES_USER:-atm}
        POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-atm}
        POSTGRES_DB: ${POSTGRES_DB:-atm}
      ports:
        - "${POSTGRES_PORT:-5432}:5432"
      volumes:
        - atm_postgres_data:/var/lib/postgresql/data
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-atm} -d ${POSTGRES_DB:-atm}"]
        interval: 5s
        timeout: 5s
        retries: 10
        start_period: 10s

  volumes:
    atm_postgres_data:
      name: atm_postgres_data
  ```

**Expected Outcome**: `docker compose up -d` поднимает postgres; через 10–20 секунд `docker compose ps` показывает `healthy`. `psql postgresql://atm:atm@localhost:5432/atm -c 'SELECT 1'` отвечает `1`.

**Verification**:
```bash
docker compose up -d
sleep 15
docker compose ps           # postgres state = healthy
docker compose exec postgres pg_isready -U atm -d atm   # accepting connections
docker compose down         # cleanup после verification (для следующих шагов — НЕ чистим)
```

**Risks**:
- Порт 5432 занят локальным Postgres на хост-машине. Митигация: в `.env.example` оставить переменную `POSTGRES_PORT=5432` и в README указать «если занят — переопределите `POSTGRES_PORT=5433` в `.env`».
- Healthcheck `pg_isready` без пароля может не работать — pg_isready не проверяет auth, это OK; но если какие-то auth-warnings вылезут, passing `-h localhost` опционально.
- При первом поднятии initdb занимает 5–15 секунд — `start_period: 10s` страхует.

**Rollback**: `docker compose down -v` (удаляет volume тоже) и `rm docker-compose.yml`.

**What**: из корня репо запустить `uv run alembic init -t async alembic`. Отредактировать `alembic.ini` (sqlalchemy.url берётся из env) и `alembic/env.py` (подставить корректный async engine, прочитать `PG_DSN` из env-переменной через `os.environ`). **Depends On**: 3 (нужен alembic + sqlalchemy[asyncio] + asyncpg в dev-group), 4 (mypy-конфиг уже ограничен `files = ["src/atm"]`, alembic/ не сканируется), 5 (нужен работающий postgres, чтобы `alembic upgrade head` выполнился в verification)

**Can-Parallel-With**: none (сериализуется после Step 4; может править pyproject.toml mypy-override при необходимости)

**Skills**: `python.md`, `sql.md` (если есть)

**Assumptions**: на момент шага 6 postgres уже поднят (Step 5 выполнен) и dev-зависимости установлены (Step 3). `sqlalchemy[asyncio]>=2.0` и `asyncpg>=0.29` присутствуют — это критично: шаблон `alembic init -t async` сразу импортирует `sqlalchemy.ext.asyncio.async_engine_from_config`, без пакетов env.py упал бы на `ImportError`.

**Implementation Notes**:
- `alembic init -t async` генерит env.py с **async-импортами из коробки** (`from sqlalchemy.ext.asyncio import async_engine_from_config, AsyncEngine`), никаких ручных правок импортов не требуется — пакеты должны просто быть установленными (Step 3 это гарантирует). См. [alembic async template](https://github.com/sqlalchemy/alembic/blob/main/alembic/templates/async/env.py) и [Alembic with Async SQLAlchemy (dev.to)](https://dev.to/matib/alembic-with-async-sqlalchemy-1ga).
- `alembic.ini`: изменить `sqlalchemy.url = ` на пустое (URL читаем из env в env.py). Установить `prepend_sys_path = .` (по умолчанию так), `file_template` оставить дефолт.
- В `alembic/env.py` сразу после `config = context.config`:
  ```python
  import os
  db_url = os.environ.get("PG_DSN") or os.environ.get("DATABASE_URL")
  if db_url:
      # Alembic env expects SQLAlchemy async URL form for asyncpg driver.
      config.set_main_option("sqlalchemy.url", db_url)
  ```
  Формат DSN для async: `postgresql+asyncpg://atm:atm@localhost:5432/atm`.
- `target_metadata` в env.py — на M0 оставить `None` (бизнес-модели появятся в M3). Можно сразу прописать заглушку:
  ```python
  # When SQLAlchemy models appear (M3), set:
  #   from atm.storage.models import Base
  #   target_metadata = Base.metadata
  target_metadata = None
  ```
- Для initial-миграции: команда `uv run alembic revision -m "initial"`. Пустой файл:
  ```python
  """initial

  Revision ID: <auto>
  Revises:
  Create Date: <auto>
  """
  from collections.abc import Sequence
  from alembic import op  # noqa: F401
  import sqlalchemy as sa  # noqa: F401

  # revision identifiers, used by Alembic.
  revision: str = "..."
  down_revision: str | None = None
  branch_labels: str | Sequence[str] | None = None
  depends_on: str | Sequence[str] | None = None


  def upgrade() -> None:
      """No-op initial migration; tables land in M3."""


  def downgrade() -> None:
      """No-op."""
  ```
- **Про mypy и alembic/**: Step 4 уже выставил `files = ["src/atm"]`, поэтому alembic/ mypy-ом не сканируется — никаких дополнительных overrides не требуется. Если в будущем решим расширить scope mypy на весь репо — добавить `[[tool.mypy.overrides]] module = ["alembic.*"] ignore_errors = true`.

**Expected Outcome**: структура `alembic/` создана, env.py готов читать `PG_DSN` из env, initial-миграция зарегистрирована и делает noop. `uv run alembic upgrade head` при поднятом Postgres отрабатывает без ImportError.

**Verification**:
```bash
uv run alembic check             # должно сказать "no new migrations to generate" или аналог (на пустом target_metadata)
# либо просто:
uv run alembic history           # показывает одну ревизию "initial"
uv run alembic upgrade head      # при поднятом postgres — exit 0 (выполнит noop)

```

**Risks**:
- `alembic init -t async` может переписать `README.md` в репозитории. Реальность: он создаёт `alembic/README` (без .md) — это отдельный файл. Проверить: ничего в корне не перезатёрто.

- Если developer забыл выполнить `uv sync` после Step 3 — `alembic` не найдёт sqlalchemy. Митигация: Verification явно требует запуск команд через `uv run`.

**Rollback**: `rm -rf alembic/ alembic.ini` (и откатить mypy-override из `pyproject.toml`, если добавляли).

  ```toml
  [tool.pytest.ini_options]
  # M0: error-on-warning оставлено сознательно; в M1+ может потребоваться ослабление

      "-ra",

      "--strict-config",

      "error",
      "ignore::DeprecationWarning:pytest_asyncio.*",
  ]
  ```

Решение — сознательное, документировано в inline-комментарии (см. выше).
- `tests/unit/test_smoke.py` (English, минимальный):
  ```python
  """Smoke test for M0 scaffolding.

  Verifies the atm package is importable and basic invariants hold.
  Does NOT require a running Postgres instance.
  """

      """atm package is installed and exposes a version string."""
      assert hasattr(atm, "__version__")
      assert atm.__version__ == "0.1.0"


  def test_python_arithmetic_sanity() -> None:
      """Absolute sanity check that the test runner works at all."""
      assert 1 + 1 == 2
  ```
- Тест **не использует** `pytest-asyncio` маркеры и async-функции — проверка, что scaffolding «дышит». Async-тесты появляются в M1.

**Expected Outcome**: `uv run pytest` собирает 2 теста, оба зелёные, exit 0.

**Verification**:
```bash
uv run pytest               # 2 passed
uv run pytest -v            # verbose: test_atm_package_importable PASSED, test_python_arithmetic_sanity PASSED
```

**Risks**:
- `filterwarnings = "error"` может внезапно провалить тест, если транзитивная зависимость на момент запуска выкинет warning. Митигация: если провалится — переключить на `default`, чётко задокументировать в комментарии.
- `asyncio_mode = "auto"` при отсутствии async-тестов безопасен (plugin просто ждёт их).

**Rollback**: удалить `tests/unit/test_smoke.py` и секцию `[tool.pytest.ini_options]` из pyproject.

## Testing Strategy

M0 не требует integration-тестов (см. Needs Integration Tests = no). Проверки — **exit criteria M0**:

1. **Smoke unit-test**: `uv run pytest` зелёный (2 теста, оба проходят).
2. **Lint**: `uv run ruff check .` — 0 errors.
3. **Format check**: `uv run ruff format --check .` — clean.
4. **Type check**: `uv run mypy src/` — "Success: no issues found".
5. **Docker-compose**: `docker compose up -d` → через ~15 с postgres healthy (`docker compose ps`).
6. **Alembic**: при поднятом postgres + корректном `.env` — `uv run alembic upgrade head` успешно выполняет noop initial-миграцию, `uv run alembic downgrade base` откатывает без ошибок. Требует `sqlalchemy[asyncio]>=2.0` + `asyncpg>=0.29` в dev-group (Step 3).
7. **End-to-end exit-criteria (из PLAN.md)**: `docker-compose up -d && uv run pytest` — зелёный.
8. **Import sanity**: `uv run python -c "import atm, atm.core, atm.llm, atm.tools.sandbox, atm.topology, atm.phases, atm.storage, atm.observability, atm.experiment, atm.evaluation, atm.analysis, atm.agents, atm.human, atm.tasks; print('ok')"` — выводит `ok`.

Развёрнутая acceptance-таблица для финального reviewer:

| Проверка | Команда | Ожидаемый exit code / output |
|---|---|---|
| uv lock + sync | `uv sync` | 0 |
| ruff lint | `uv run ruff check .` | 0, "All checks passed!" |
| ruff format check | `uv run ruff format --check .` | 0 |
| mypy | `uv run mypy src/` | 0, "Success: no issues found" |
| pytest | `uv run pytest` | 0, "2 passed" |
| docker-compose | `docker compose up -d && docker compose ps` | postgres status=healthy |
| alembic noop | `PG_DSN=... uv run alembic upgrade head` | 0 |
| package import | `uv run python -c "import atm; print(atm.__version__)"` | `0.1.0` |

## Open Questions

1. **Точные версии зависимостей в pyproject.toml**. Plan указывает нижние границы (`>=0.9`, `>=1.14`, etc.). Нужно ли фиксировать верхние границы (`<2.0`)? По community-практике 2026 — нижние границы ОК, верхние добавляются только при известных breaking changes. **Предложение**: не добавлять верхние границы до первого breaking-change инцидента; оставить dependabot/renovate policy на будущее.

2. **`filterwarnings = "error"` в pytest**. Может слишком агрессивно для M1+ (особенно когда появятся `sqlalchemy 2.x` с `MovedIn20Warning` и `pytest-asyncio` deprecations). **Предложение**: оставить в M0, будет ослаблено по факту в первом же тесте, который поднимет warning. Комментарий об этом уже добавлен в `[tool.pytest.ini_options]` (Step 8).

3. **`tests/fixtures/__init__.py` или `.gitkeep`?** Я выбрал `__init__.py` (пакет), чтобы shared-фикстуры из M2+ импортировались как `from tests.fixtures.llm import scripted_response`. Альтернатива — `conftest.py` на уровне `tests/` без пакетного `fixtures/`. **Предложение**: оставить пакет; если на M2 потребуется изменить — отдельное решение.

4. **Стоит ли в M0 добавить precommit (например, `pre-commit`)?** Чеклист M0 не требует. **Решение**: не добавлять; это отдельная opinionated конфигурация, можно включить в M1+ если команда захочет.

5. **`conf/`-подкаталоги**. Решено в Step 2: создаём `conf/{topology,agents,task,model,experiment}/.gitkeep` (не Python-пакеты). YAML-файлы с реальными конфигами появятся в M1+.

6. **Версия Postgres image**. `postgres:16-alpine` vs `postgres:16`. Alpine меньше, но glibc-совместимость иногда подводит на экзотических arch. **Предложение**: оставить `16-alpine` (актуально для linux-хостов dev-команды).
